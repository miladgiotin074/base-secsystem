خط لولهٔ کلی FormScan

ورودی فقط پکیج اپ تحت رصد و سرویس Accessibility است. خروجی یک FormLook با چهار بخش است: main، eye، password، و لیست فیلدهای editable.

1

پنجره‌های APPLICATION همان پکیج

فقط TYPE_APPLICATION با packageName == pkg. ریشهٔ هر پنجره جمع می‌شود.

2

DFS روی درخت نودها → Fact

برای هر نود با ابعاد مثبت: متن، hint، desc، viewId، کلاس، clickable/editable/password/checkable و مختصات صفحه.

3

فیلتر EditTextها (از بالا به پایین)

اگر هیچ فیلد editable نباشد، main/eye/password همه null می‌مانند.

4

password → eye → main

ترتیب اجباری است: اول فیلد رمز، بعد چشم نسبت به همان فیلد، بعد دکمهٔ اصلی با حذف تداخل با چشم.

شناسایی فیلد رمز password

  • نود editable است (isEditable یا کلاس شامل EditText).
  • و یکی از این‌ها: isPassword == true، یا در blob متن/آیدی/hint کلمه‌های password / passwd / رمز / گذرواژه دیده شود.
  • اگر چند فیلد رمز باشد، کوچک‌ترین مساحت انتخاب می‌شود (minBy(width × height)) — معمولاً همان فیلد رمز لاگین است نه کادر بزرگ.

بدون فیلد رمز معتبر، چشم اصلاً جستجو نمی‌شود.

شناسایی دکمهٔ چشم eye

روی همهٔ Factها (نه فقط دکمه‌ها) امتیاز eyeScore حساب می‌شود و بالاترین امتیاز انتخاب می‌شود؛ فقط اگر امتیاز نهایی ≥ ۴۵ باشد.

حذف قطعی (امتیاز صفر)

  • خود نود password یا editable باشد.
  • عرض نود ≥ عرض فیلد رمز باشد (چشم باید باریک‌تر از فیلد باشد).
  • عرض نود صفر یا منفی باشد.

شناسایی دکمهٔ اصلی main

تابع pickMainButton از بین Factها کاندیدا می‌سازد، ردیف‌های متنی زائد را هرس می‌کند، سپس نزدیک‌ترین دکمهٔ «شبیه ورود» از بالا را برمی‌گرداند.

۱) تعریف محدودهٔ فرم

  • Editهایی که عرض > ۴۰ و روی صفحه دیده می‌شوند.
  • formBottom = پایین‌ترین لبهٔ این فیلدها.
  • حداقل عرض دکمه: حدود ۲۸٪ عرض صفحه (یا اگر loginHint باشد، حداقل ۴۸px).

۲) فیلتر کاندیدا

  • editable یا password نباشد.
  • با مستطیل چشم تداخل نداشته باشد (و همان نود چشم نباشد).
  • کلیک‌پذیر باشد؛ مگر اینکه loginHint باشد و اکشن کلیک داشته باشد.
  • ارتفاع بین ۲۴px و نصف عرض صفحه.
  • بالای دکمه تقریباً زیر فرم باشد: top ≥ formBottom − height/4 (یعنی دکمهٔ بالای فیلدها رد می‌شود).
  • مرکز هیچ فیلد editable داخل دکمه نباشد (کادر دور فرم نیست).

۳) تشخیص «ورود» — isLoginMain

  • viewId شامل login باشد، یا
  • متن/desc شامل «ورود» باشد، یا
  • یک TextView با متن «ورود» داخل جعبهٔ ۱۲dp دور همان نود باشد (دکمهٔ بدون متن روی لایهٔ زیر).

۴) هرس ردیف متنی نازک

اگر ارتفاع کاندیدا ≤ حدود ۳۶dp باشد و loginHint نباشد، فقط وقتی نگه داشته می‌شود که کاندیدای دیگری دقیقاً زیرش نباشد — تا برچسب متنی بالای دکمه به‌جای خود دکمه انتخاب نشود.

۵) انتخاب نهایی

بین باقی‌مانده‌ها: اول اولویت با loginHint، بعد بالاترین top (نزدیک‌ترین دکمهٔ ورود به فیلدها از بالا).

استفاده در جریان رصد

M

MainTapOverlay روی main

وقتی هم main و هم password پیدا شود و (چشم باشد یا رمز هنوز سانسور باشد)، یک لایهٔ شفاف فقط روی دکمهٔ اصلی می‌نشیند تا قبل از ارسال، EyeReveal اجرا شود.

E

EyeReveal

اگر متن فیلد هنوز masked باشد (• ● * …)، روی چشم کلیک می‌شود، متن خوانده می‌شود، دوباره چشم کلیک می‌شود تا masked برگردد، بعد ضربهٔ دکمهٔ اصلی replay می‌شود.

D

دیباگ موقت — watchMarkEye

اگر در config.json مقدار watchMarkEye: true باشد، مستطیل چشم با کادر صورتی غیرقابل‌لمس مشخص می‌شود تا صحت تشخیص دیده شود.

نکتهٔ عملی: اشتباه رایج در تشخیص چشم معمولاً از کم‌بودن امتیاز (کلمهٔ کلیدی OEM غایب + فاصله از لبهٔ فیلد) یا قاطی شدن با آیکن کناری دیگر است. برای دکمهٔ اصلی، متن «ورود» روی لایهٔ جدا یا عرض کمتر از ۲۸٪ صفحه باعث از دست رفتن کاندیدا می‌شود.
